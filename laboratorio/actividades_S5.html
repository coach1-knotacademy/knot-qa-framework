Cómo leer una prueba sin saber programar

2 min · para tener a mano toda la clase

No hace falta escribir TypeScript para entender una prueba. Con estas siete piezas se lee casi todo el framework.

async / await«espera a que este paso termine antes de seguir», como en el caso manual: un paso a la vez.
{ paginaRecargas, cliente }las piezas que la prueba pide; alguien más se las entrega (los fixtures, la D de la S4).
paginaRecargas.recargar(...)«a esta pantalla, pídele que haga esto». El punto separa quién de qué hace.
class · newla clase es el molde; new saca un objeto del molde.
privatesolo la clase lo toca. Las pruebas no ven los localizadores.
this.«lo mío»: el campo o el método de esta misma clase.
.desde(...).hacia(...).por(...)una frase de negocio dicha en pedazos: «transferir desde la principal hacia ahorros por 50».

CP-021 · Recarga de $60.000 a celular con código

Precondición: Ana tiene $1.500.000 en Ahorros. Resultado esperado: comprobante con «Valor: $60.000» y el saldo baja $60.000.

1La dirección del ambiente de pruebas: http://127.0.0.1:4000
Configuración. Vive una sola vez en src/config/entorno.ts. Si mañana el ambiente cambia, se corrige ahí.
2El usuario ana y la clave Clave123
Datos. Salen de usuarios.ana. La prueba no escribe la clave a mano.
3Escribir usuario y clave y pulsar Ingresar
Pantalla. Es PaginaLogin.ingresar(). Los localizadores viven ahí y en ningún otro lado.
4Iniciar sesión completa: login, leer el SMS y escribir el código
Tarea. Son varios pasos de pantalla con un nombre de negocio: iniciarSesionPorUi(). En Screenplay sería una tarea IniciarSesion.
5Operador Claro, celular 3001234567 y valor $60.000
Datos. Es fabricaDeRecargas.grande(): la fábrica sabe que «grande» es más de $50.000.
6Elegir operador, escribir celular y valor, y pulsar Recargar
Pantalla. Es PaginaRecargas.recargar(recarga).
7Recarga con código: pedirlo, leerlo del SMS y confirmar
Tarea. Un paso de negocio que junta pantalla y buzón. Si la regla del código cambia, se corrige en un solo lugar.

Pantalla = Page Object · Tarea = un paso de negocio (flujo o Screenplay) · Datos = Factory · Configuración = un solo lugar para el ambiente.

Page Object

Lo construyeron en la S3: PaginaLogin, PaginaOtp y PaginaTransferir (retos 1 a 3). Hoy le ponemos nombre y reglas.

El problema que ya sufrías a mano
Cambian el botón «Ingresar» por «Entrar» y hay que corregir 40 casos en el ALM.
La idea, en una frase
El manual de una pantalla: lo que la pantalla tiene (campos, botones) y lo que sabe hacer (transferir, recargar). La prueba dice qué; la página sabe cómo.
Sus partes, en el repo
Localizadores private (lo que tiene) · métodos con nombre de negocio, como recargar() (lo que sabe hacer) · su ruta · hereda de PaginaBase.
Sí, cuando
Toda pantalla que usa más de una prueba.
No, cuando
Con expect adentro: la página no decide si algo está bien, eso lo dice la prueba. Tampoco una sola clase gigante para todo el sitio.
La frase para tu líder
«Si rediseñan el portal de transferencias, se arregla un archivo, no 200 casos.»
Cómo pedírselo a la IA
«Usa PaginaRecargas; no escribas localizadores dentro de la prueba.»

ejemplo resuelto · la pantalla «Transfer Funds» de ParaBank

Lo que la pantalla tiene son los localizadores private. Lo que sabe hacer es el método transferir(). La prueba nunca ve un localizador.

/** "Transfer Funds": mueve plata entre dos cuentas del mismo cliente. */
export class PaginaTransferirParaBank extends PaginaParaBank {
  readonly ruta = 'transfer.htm';
  /** El recuadro "Transfer Complete!" con el detalle. */
  readonly resultado: Locator;
  private readonly campoMonto: Locator;
  private readonly listaDesde: Locator;
  private readonly listaHacia: Locator;
  private readonly botonTransferir: Locator;

  constructor(page: Page) {
    super(page);
    this.resultado = page.locator('#showResult');
    this.campoMonto = page.locator('#amount');
    this.listaDesde = page.locator('#fromAccountId');
    this.listaHacia = page.locator('#toAccountId');
    this.botonTransferir = page.getByRole('button', { name: 'Transfer' });
  }

  async transferir({ monto, desde, hacia }: { monto: number; desde: number; hacia: number }): Promise<void> {
    await this.esperarOpciones(this.listaHacia);
    await this.campoMonto.fill(String(monto));
    await this.listaDesde.selectOption(String(desde));
    await this.listaHacia.selectOption(String(hacia));
    await this.botonTransferir.click();
    await this.resultado.or(this.page.locator('#showError')).first().waitFor();
  }
}

ficha · 3 mincapa de la S3: src/datos/

Factory

En la S3 era usuarios.ana: datos con nombre en un solo lugar. La fábrica es el paso siguiente.

El problema que ya sufrías a mano
«El usuario de pruebas de siempre» ya lo usó otro y la prueba falla. O la hoja de datos tiene 30 copias del mismo monto y nadie sabe por qué es 60.000.
La idea, en una frase
Pides los datos por su nombre de negocio («una recarga grande») y la fábrica te entrega un objeto nuevo y válido cada vez.
Sus partes, en el repo
valida(), el molde con valores por defecto · variantes con nombre: grande(), aOperadorCaido() · cambios: solo escribes lo que le importa a esa prueba.
Sí, cuando
Datos que se repiten o que tienen reglas: el monto que pide código, el límite diario, un cliente único por corrida en ParaBank.
No, cuando
Un dato que usa una sola prueba. Nunca datos copiados de producción: datos personales reales (habeas data).
La frase para tu líder
«Si el banco sube el umbral del código a $80.000, se cambia un número, no 30 pruebas. Y ningún dato sale de producción.»
Cómo pedírselo a la IA
«Los datos salen de fabricaDeRecargas; no escribas montos ni números a mano.»

ejemplo resuelto · src/datos/fabricaDeRecargas.ts

valida() es el molde. grande() no repite nada: pide el molde y cambia solo el monto. Los tres puntos (...cambios) dejan que cada prueba cambie lo que le importa.

export const fabricaDeRecargas = {
  valida(cambios: Partial<Recarga> = {}): Recarga {
    return { operador: 'Claro', numero: numerosDePrueba.normal, monto: montos.normal, ...cambios };
  },

  /** Una recarga de más de $50.000: el banco pide un código antes de hacerla. */
  grande(cambios: Partial<Recarga> = {}): Recarga {
    return fabricaDeRecargas.valida({ monto: montos.conCodigo, ...cambios });
  },
  // … aOperadorCaido() y paraCadaOperador() siguen el mismo molde
};

ficha · 3 mincapa de la S3: src/flujos/ → src/screenplay/

Screenplay

En la S3, iniciarSesionPorUi() ya era una tarea, aunque no se llamara así. Screenplay ordena todas las tareas alrededor de quien las hace.

El problema que ya sufrías a mano
El caso dice «Ana transfiere $50 a ahorros», pero la prueba son 12 clics que no cuentan la historia. Y con dos roles (quien crea y quien aprueba) se vuelve un enredo.
La idea, en una frase
La prueba contada por un actor: quién (Actor), con qué (Habilidad), qué hace (Tarea) y qué revisa (Pregunta).
Sus partes, en el repo
Actor.llamado('Ana') · .puede(...) le da una Habilidad (el navegador, la API) · .intenta(...) hace Tareas · .pregunta(...) responde Preguntas.
Sí, cuando
Hay varios roles con habilidades distintas. Ejemplo: doble autorización (maker-checker), donde un cliente crea una transferencia sobre el tope y un aprobador la autoriza. También prepara BDD (S7).
No, cuando
Una suite pequeña con un solo rol: Page Object y flujos bastan. No es mejor ni peor: se usan juntos, porque una tarea usa un Page Object por dentro.
La frase para tu líder
«La prueba se lee como el caso del ALM: el negocio la puede revisar sin saber programar.»
Cómo pedírselo a la IA
«Escribe la prueba con un Actor y las tareas de src/screenplay/.»

ficha · 3 mincapa de la S3: src/config/

Singleton

En la S3, entorno.ts ya era único: la dirección del ambiente en un solo lugar.

El problema que ya sufrías a mano
Cada tester anota su propia URL del ambiente: uno prueba en QA y otro, sin saberlo, en UAT.
La idea, en una frase
De algunas cosas debe existir una sola: la configuración. De otras, una por prueba: el navegador, la sesión y el cliente.
Sus partes, en el repo
Un solo objeto entorno (dirección, usuario, tiempos) que se lee de variables de entorno. En TypeScript un módulo ya es único: no hace falta la clase con getInstance().
Sí, cuando
La configuración de cada ambiente (QA, UAT) y las reglas de convivencia con un sitio real, como la pausa entre pruebas para que ParaBank no responda 429.
No, cuando
Un navegador o una sesión compartidos (DriverManager.getInstance()): en paralelo, una prueba puede ver la cuenta de otro cliente. Es un incidente de confidencialidad, no una prueba inestable.
La frase para tu líder
«Nadie corre contra producción por error: el ambiente vive en un solo lugar.»
Cómo pedírselo a la IA
«La dirección sale de la configuración; nunca la escribas dentro de la prueba.»

ejemplo resuelto · src/config/entorno.ts

Un módulo de TypeScript se carga una sola vez: este objeto ya es único. Cada valor se puede cambiar con una variable de entorno sin tocar el código.

export const entorno = {
  /** Dirección del Banco Demo. */
  urlBase: process.env.URL_BANCO ?? 'http://127.0.0.1:4000',

  /** Usuario principal de las pruebas. */
  usuario: process.env.USUARIO_BANCO ?? 'ana',

  /** Clave de los usuarios de práctica. En un proyecto real, nunca la escribas en el código. */

El mismo pedido, con la IA dentro del repo

Leyó .github/copilot-instructions.md y los Page Objects. Resultado al correrla: verde. Agregó sola el paso del código, porque lo encontró en la regla.

import { cuentas, usuarios } from '../../src/datos/usuarios';
import { fabricaDeRecargas } from '../../src/datos/fabricaDeRecargas';
import { iniciarSesionPorUi } from '../../src/flujos/sesion';
import { test, expect } from '../../src/soporte/fixtures';

const pesos = (valor: number): string => `$${valor.toLocaleString('es-CO')}`;

test.describe('Recarga de celular con ingreso completo por la pantalla', () => {
  test('Ana recarga $60.000 a Claro con código de seguridad y el saldo de Ahorros baja', async ({
    paginas,
    paginaRecargas,
    cliente,
  }) => {
    // Ingreso por la UI: login, OTP leído del buzón y llegada al inicio.
    await iniciarSesionPorUi(paginas, usuarios.ana);

    await paginaRecargas.abrir();
    await expect(paginaRecargas.saldoDisponible).toHaveText(pesos(cuentas.ahorros.saldoInicial));

    // Claro, 3001234567 y $60.000 salen de la fábrica (recarga "grande").
    const recarga = fabricaDeRecargas.grande();
    await paginaRecargas.recargar(recarga);

    // Más de $50.000: el banco pide un segundo código, que llega al buzón.
    await expect(paginaRecargas.campoCodigo).toBeVisible();
    await paginaRecargas.confirmar(await cliente.leerCodigo(usuarios.ana.usuario));

    const comprobante = await paginaRecargas.esperarResultado();
    expect(comprobante).toContain('Recarga exitosa');
    expect(comprobante).toContain(`Valor: ${pesos(recarga.monto)}`);

    // El saldo esperado sale de la regla: saldo inicial menos el valor de la recarga.
    await expect(paginaRecargas.saldoDisponible).toHaveText(pesos(cuentas.ahorros.saldoInicial - recarga.monto));
  });
});

¿Y si le pedimos «déjamela en verde»?

«La app reporta total $100.400, pero a la Corriente solo le descontó $100.000. Si hubiera puesto 150.000, habría quedado verde, pero se estaría dando por bueno el comportamiento actual sin confirmar la regla de negocio.»

Bloqueos reales que encontramos (y cómo los maneja el framework)

  • Límite de peticiones. ParaBank está detrás de Cloudflare: con demasiadas peticiones seguidas responde HTTP 429 y bloquea 5 minutos. El framework va de a una prueba, con una pausa que vive en la configuración, y si llega un 429 lo dice claro.
  • Datos compartidos. Cualquier persona del mundo usa ParaBank. Si todas las pruebas usan «el usuario de siempre», se pisan. La fábrica crea un cliente nuevo por corrida.
  • Bugs reales. ParaBank deja transferir más de lo que hay y acepta montos negativos (PB-01 y PB-02). Las pruebas dicen lo que debería pasar.
  • Código extra y límite diario en las recargas del Banco Demo, como en una billetera real.
  • Un tercero que no responde. Si el operador no contesta, ¿se pierde la plata? En el Banco Demo, sí (BUG-04). Y con page.route se puede «apagar» un servicio para probar qué pasa.

ParaBank es público: nunca escriban ahí datos reales.
