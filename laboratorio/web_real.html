Si tu equipo te deja abrir F12

  1. Clic derecho sobre el buscador → Inspeccionar. Mira el <label> y el atributo data-test: son lo que usa el Page Object.
  2. En la pestaña Elements, a la derecha, abre Accessibility: ves el rol y el nombre del elemento. Si el nombre está vacío, getByRole con nombre y getByLabel no lo van a encontrar.
  3. Haz lo mismo en el carrito sobre la cantidad: se llama «Quantity for Pliers». Ese nombre accesible es el que busca la prueba.

El código, por capas

Las mismas capas del framework de la S3, en src/sitios/toolshop/: la configuración (entorno.ts, con la dirección), los datos (fabricaDeLaTienda.ts), las páginas (paginas/, una por pantalla) y las piezas de cada prueba (fixtures.ts). La prueba solo dice el negocio.

el page object del catálogo

src/sitios/toolshop/paginas/PaginaCatalogo.ts

import { Locator, Page } from '@playwright/test';
import { PaginaToolshop } from './PaginaToolshop';

/**
 * El catálogo (la página de inicio): buscar, filtrar por categoría y abrir un producto.
 * Todos los localizadores salen de lo que ve la persona: rol + nombre o etiqueta.
 */
export class PaginaCatalogo extends PaginaToolshop {
  readonly ruta = '';
  /** El título que confirma la búsqueda: «Searched for: Pliers». */
  readonly tituloDeLaBusqueda: Locator;
  /** Los nombres de los productos que se ven ahora (cada tarjeta tiene su título). */
  readonly nombresDeProductos: Locator;
  private readonly buscador: Locator;
  private readonly botonBuscar: Locator;

  constructor(page: Page) {
    super(page);
    this.buscador = page.getByRole('textbox', { name: 'Search' });
    // exact: también existe el botón «X» para limpiar, y textos que contienen "Search".
    this.botonBuscar = page.getByRole('button', { name: 'Search', exact: true });
    this.tituloDeLaBusqueda = page.getByRole('heading', { name: /^Searched for:/ });
    this.nombresDeProductos = page.getByRole('heading', { level: 5 });
  }

  /** La tarjeta de un producto: el enlace que tiene su título. */
  private tarjeta(nombre: string): Locator {
    return this.page.getByRole('link').filter({ has: this.page.getByRole('heading', { level: 5, name: nombre, exact: true }) });
  }

  async buscar(texto: string): Promise<void> {
    await this.buscador.fill(texto);
    await this.botonBuscar.click();
  }

  /** Marca una categoría del filtro «By category» (por ejemplo «Hammer»). */
  async filtrarPorCategoria(categoria: string): Promise<void> {
    await this.page.getByRole('checkbox', { name: categoria, exact: true }).check();
  }

  /**
   * ¿Todos los productos que se ven tienen ese texto en el nombre? (sin importar mayúsculas)
   * Ojo: la lista se actualiza DESPUÉS de buscar o filtrar. Por eso la prueba usa expect.poll,
   * que vuelve a preguntar hasta que la lista nueva aparece (y falla si nunca aparece).
   */
  async todosLosProductosDicen(texto: string): Promise<boolean> {
    const nombres = (await this.nombresDeProductos.allInnerTexts()).map((n) => n.trim());
    return nombres.length > 0 && nombres.every((n) => n.toLowerCase().includes(texto.toLowerCase()));
  }

  /** El precio que muestra la tarjeta del producto en el catálogo, como número. */
  async precioEnElCatalogo(nombre: string): Promise<number> {
    // Peldaño 4 (test-id pactado): el precio cambia, no hay un texto fijo que buscar.
    return this.aNumero(await this.tarjeta(nombre).getByTestId('product-price').innerText());
  }

  async abrirProducto(nombre: string): Promise<void> {
    await this.tarjeta(nombre).click();
  }
}

Fíjate en todosLosProductosDicen: la lista se actualiza después de buscar. Al explorar el sitio, el primer script buscó «Thor Hammer», leyó la lista vieja y abrió «Combination Pliers». La prueba lo resuelve con expect.poll, que vuelve a preguntar hasta que aparece la lista nueva. Es una espera real, no un waitForTimeout.

Y un error real de la primera corrida: el CP-501 se quedó minutos esperando el evento load de la página, porque un recurso de un tercero (chat, analítica) no terminaba de cargar. Por eso abrir() (en PaginaToolshop.ts) espera solo domcontentloaded y cada prueba espera lo que de verdad necesita. En un sitio real, eso pasa.

/**
 * Kit «web real» · Toolshop: agregar al carrito y verificar la cantidad y el total (CP-504).
 * Escenario en especificaciones/toolshop.feature. La prueba se detiene en el carrito: no se compra.
 *
 * El esperado sale de la REGLA (total = precio unitario × cantidad), no de copiar lo que mostró la pantalla.
 *
 * Correr:  npx.cmd playwright test --project=toolshop -g "CP-504"
 */
import { fabricaDeCompras } from '../../src/sitios/toolshop/fabricaDeLaTienda';
import { test, expect } from '../../src/sitios/toolshop/fixtures';

test('CP-504 · Dos unidades en el carrito suman el doble del precio', { tag: '@CP-504' }, async ({ catalogo, producto, carrito }) => {
  const compra = fabricaDeCompras.dosUnidades();
  let precio = 0;

  await test.step('Dado que Ana tiene el carrito vacío', async () => {
    await catalogo.abrir();
    await expect(catalogo.nombresDeProductos.first()).toBeVisible();
    await expect(catalogo.unidadesEnElCarrito).toHaveCount(0);
  });

  await test.step(`Cuando lleva ${compra.cantidad} unidades de «${compra.producto}» al carrito`, async () => {
    await catalogo.abrirProducto(compra.producto);
    await expect(producto.nombre).toHaveText(compra.producto);
    precio = await producto.precioUnitario();
    await producto.agregarAlCarrito(compra.cantidad);
    await expect(producto.avisoAgregado).toBeVisible();
    await expect(producto.unidadesEnElCarrito).toHaveText(String(compra.cantidad));
    await producto.irAlCarrito();
  });

  await test.step(`Entonces el carrito muestra ${compra.cantidad} unidades de «${compra.producto}»`, async () => {
    await expect(carrito.cantidadDe(compra.producto)).toHaveValue(String(compra.cantidad));
  });

  await test.step(`Y el total es ${compra.cantidad} veces el precio unitario`, async () => {
    const esperado = `$${(precio * compra.cantidad).toFixed(2)}`;
    await expect(carrito.totalDeLaFila(compra.producto)).toHaveText(esperado);
    await expect(carrito.total).toHaveText(esperado);
  });
});

Qué se encontró: los campos no tienen nombre accesible

La causa, en el HTML: el id se repite. El componente <nequi-input id="phoneNumber"> y el <input id="phoneNumber"> de adentro tienen el mismo id, y <label for="phoneNumber"> apunta al primero, que es un envoltorio y no un campo. La prueba lo deja medido:

Lo que esto significa para una persona: un lector de pantalla dice «campo de número» sin decir cuál. No es un problema de la prueba: es un hallazgo de accesibilidad. Y el mensaje de error tampoco está asociado al campo (sin aria-describedby): se ve, pero no se anuncia.

la recomendación profesional

«Pedir a desarrollo un <label for> que apunte al <input> (con un id único) o un aria-label. Arregla la prueba y, además, es accesibilidad.» Mientras tanto, la prueba usa un localizador un peldaño más abajo y lo protege (ver la escalera).

Otras cosas que vio la exploración (sin automatizar)

  • El aviso del mínimo dice «Debes ingresar mín. [$1]», con corchetes: parece una plantilla de texto sin terminar. Es cosmético; se reporta igual.
  • El formulario no muestra un valor máximo: $999.999.999 no da aviso. Si hay tope, se valida después de «Continuar», que no pulsamos. No lo sabemos, y no lo inventamos.
  • Un celular de 10 dígitos que empieza por 1 no da aviso; uno de 11 dígitos queda inválido, pero sin mensaje. Son preguntas para el negocio, no bugs confirmados.

Qué no se automatiza, y por qué

Saber dónde parar también es parte del trabajo de un QA. Esto se decidió antes de escribir la primera línea:

QuéPor qué no
La casilla «Confirmo que soy una persona real»Es un control antibots. Existe justo para que un robot no pase. Automatizarlo sería atacar el control, no probarlo. En un sistema propio, el equipo pide a desarrollo una llave de pruebas o un ambiente sin antibots; nunca se «salta».
«Continuar» y el pago por PSEDel otro lado hay un banco y dinero real. Pagar no es una prueba de validación: es una transacción. Eso se prueba en el ambiente de pruebas del dueño del sistema, con su permiso.
Lo que pasa después (el banco, el comprobante)Es producción de un tercero: no tenemos su permiso, ni datos de prueba, ni un ambiente para hacerlo. Ningún gerente firma evidencia sacada de producción ajena.
Carga, estrés o muchas corridasCien corridas seguidas contra producción ajena parecen un ataque. Se corrió pocas veces, de a una prueba y con pausa.

El código lo hace cumplir: el Page Object del formulario real no tiene un método para pulsar «Continuar» ni para marcar la casilla. Si no existe el método, ninguna prueba lo puede hacer por error.

La escalera de la S6, en un sitio real

Los mismos cinco peldaños de los localizadores robustos. En la Toolshop se usan los de arriba; en el formulario real, el peldaño 2 no funciona y hay que bajar uno, sabiendo qué se arriesga.

  1. 1
    Rol + nombre
    getByRole('button', { name: 'Recargar' })

    en la toolshop

    getByRole('button', { name: 'Add to cart' }) · getByRole('checkbox', { name: 'Hammer' })

    en el formulario real

    getByRole('button', { name: 'Continuar' }) sí funciona: el botón tiene nombre. Los campos, no: salen como spinbutton sin nombre.
  2. 2
    Etiqueta
    getByLabel('Número de celular')

    en la toolshop

    getByLabel('Email address') · getByLabel('First name'): cada campo tiene su <label>.

    en el formulario real

    getByLabel('Número de celular') → 0 elementos. La etiqueta existe, pero apunta a un id repetido (el del envoltorio, no el del campo).
  3. 3
    Texto
    getByText('Recarga exitosa')

    en la toolshop

    getByText('Email format is invalid') para los mensajes de validación.

    en el formulario real

    getByText('¡Ups! Esos dos números no coinciden, porfa revísalos.') para el mensaje. Funciona.
  4. 4
    Test-id pactado
    getByTestId('saldo-disponible')

    en la toolshop

    getByTestId('cart-total'): el sitio trae data-test pactados. En la configuración: testIdAttribute: 'data-test'.

    en el formulario real

    No hay test-id. Lo que usamos: getByRole('spinbutton').nth(0). Rol sí, nombre no: depende del orden, como nth-child. Por eso el Page Object revisa que haya exactamente 2 campos numéricos antes de escribir.
  5. 5
    CSS o XPath: nunca
    locator('.btn-azul') · locator('form > input:nth-child(4)') · locator('xpath=/html/body/main/form/button')

    en la toolshop

    No hizo falta.

    en el formulario real

    locator('input#phoneNumber') también funcionaría, pero ese id ya está repetido una vez: no es un contrato. No se usa.

Las reglas de ética

  • Sin carga ni estrés. Una prueba a la vez (workers: 1), con pausa, y pocas corridas. El sitio no es tuyo.
  • Sin enviar. Solo validaciones: se mira lo que el formulario dice antes de mandar. Nunca «Continuar».
  • Sin datos reales. Celulares de prueba evidentes, como 3000000000. Nunca el tuyo ni el de un cliente.
  • Respeta el antibots. Si el sistema pregunta «¿eres una persona?», ahí se detiene la automatización, a propósito.
  • Producción ajena no es tu ambiente de pruebas. Lo que se muestra aquí es un ejemplo de lectura y validación. Para tu trabajo: el ambiente de pruebas de tu equipo y con permiso.
  • En el banco, nunca sus sistemas desde aquí. Ni datos, ni pantallas, ni grabaciones del banco, tampoco en la IA.
